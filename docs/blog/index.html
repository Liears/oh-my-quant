我们为什么保留自己的 Harness，却不再维护模型协议

初稿 2026-10-12 · 修订 2026-10-14 · oh-my-quant · Markdown 原文

连接模型、注册工具，可以让量化 Agent 开始回答。要让它在取消、配置变化和报告恢复之后继续正确工作，还需要决定：谁为一次研究的完整生命周期负责。

接入内核之后，应用还应该拥有什么？

Pi 已经提供模型协议和低层执行循环。复用它，意味着 oh-my-quant 不必自行追赶每种供应商的流式格式、工具调用协议与模型目录。这是明确的收益，也让「尽量采用上游能力」成为合理起点。

但量化研究的状态比一次模型调用活得更久。用户会在工具执行时补充问题，会修改模型连接，也会打开昨天的报告，要求从当时的分支继续。内核能运行工具，不代表它知道这些动作该怎样改变 WhyJ 的研究状态。

Lilian Weng 用 planning、memory、tool use 建立了 Agent 的能力地图。构建应用时，我们需要在这张地图上再标出所有者：谁准备资源，谁提交状态，谁在失败后保住当前工作。LLM Powered Autonomous Agents

最后一个 token，不是研究的终点

只沿着调用链看，模型返回最后一个 token，操作似乎就完成了。但结果可能尚未落盘，监听器还在运行，用户此时又发起了恢复。若 busy 只覆盖流式输出，准备和收尾阶段就可能失去保护，旧结果也可能写入已经切换的分支。

把这些规则全部放进模型回调，能够就地处理问题，却会让协议适配承载越来越多产品语义。反过来，把整个循环复制到项目里，虽然获得了修改自由，也把供应商兼容与后续升级变成自己的长期责任。

因此，这不是「要不要模块化」的抽象选择，而是两种变化是否应该由同一层承担。模型协议变化，与研究分支、报告恢复规则变化，并没有相同的节奏。

旧重构路线也曾提出分阶段拆分。重新核对时，我们发现“文件更短”和“模块可替换”被放得太近了：前者可以靠移动代码完成，后者却需要一个不依赖默认本地宿主的真实实现来验证。因此保留的是先治理依赖、再按变化压力抽服务的顺序，不是旧 P0–P3 文件清单。目录结构是结果，不能替代对所有者和副作用的判断。

复用循环，把领域生命周期留在应用侧

现在，kernel/loop.ts 接入 Pi 循环，kernel/llm.ts 接入模型协议与目录；WhyJ 的 session-runtime 管理队列、分支、压缩与操作生命周期。QuantAgentSession 接收模型、工具、技能、存储和核验端口，TUI 订阅状态，不直接编辑会话树。

图 1：协议复用没有消除应用状态；边界把两类变化分开。箭头是调用或数据流，不表示独立部署。

在 Harness 内，一次操作包围资源准备、执行、持久化和需要等待的监听器。概念上，它比一次模型请求更长：

const finish = operation.start("turn");
try {
  const resources = await prepare(operation.signal);
  await run(resources, operation.signal);
  await flush(); // 收到最后一个 token 后，仍须完成必要的提交。
} finally {
  finish();
}

这段示意不是现有实现的替代代码，也不是一个覆盖所有入口的事务。QuantAgentSession.prompt() 在进入 harness.prompt() 前还会同步模型、技能和研究投影；waitForIdle() 等待 Harness 操作，不保证 facade 全部前置工作都已串行化。这个缺口应该明确留下，不能因为有了 HarnessOperation 就宣布并发问题全部解决。

配置更新采用相同的思路：独立 prompt、skill 和手动压缩准备连接快照；在途循环与排队续问保持原连接。工具和技能在允许的空闲边界更新，准备失败保留旧资源。否则，一次请求可能使用旧 endpoint，却在下一步读到新 key。

迁移曾让这个边界暴露得更具体：更新依赖版本并不意味着请求已使用新协议，旧路径别名仍可能把调用导向本地副本；Pi 的 TranscriptContext 也要求摘要入口一起迁移。只修主对话而不检查压缩，是把“能开始回答”错当成“整个会话已经升级”。现行版本因此只从依赖声明读取，升级核对的是入口与行为，而不再由几篇文档各自记一个版本号。

事件也是同样的陷阱。读取流式事件能看见 assistant 输出，却不天然阻止下一步工具执行；如果落盘还在异步队列里，任务守卫就可能读到旧分支。现在用可等待的事件 sink，把 assistant 提交完成放在工具预检之前，并用故意延迟提交的回归验证顺序。代价是持久化进入关键路径，换来的是守卫有明确的事实读取点，而不是“事件大概已经处理了”。消息屏障回归

我们因此放弃了「所有动作立即切到最新配置」的直觉，选择「一次操作使用可解释的资源版本」。取消也一样：abort 只是发出停止请求，摘要提交、leaf 移动和状态发布前仍要核对操作有效性。

可替换的边界，也有维护成本

已有独立宿主回归用内存 repo 和自定义工具运行真正的 Pi 循环。它证明会话端口可以被实际替换，不只是接口定义允许替换；但这不证明所有模块已经独立发布，也不证明并发入口已经完全事务化。会话依赖注入与验证

从维护角度看，这次选择有一笔不能省略的账：

路径主要收益留给团队的责任
自己维护协议与循环最大修改自由供应商差异、协议演进、兼容测试
全面采用上游应用运行时减少本地生命周期实现将研究分支与报告契约迁入其状态模型
当前的内核复用、应用运行时自有两类变化相对分离适配层、事件映射、取消与恢复回归

Pi AI / Agent Core 的具体版本以 依赖声明为准，升级仍需要验证类型、事件映射与完整生命周期，不能把“版本号已更新”当作迁移完成；WhyJ 也没有因此兼容 Pi 原生 ExtensionAPI。内核适配边界

文档也需要遵循同一边界。Agent Runtime 设计解释怎样执行、取消和提交；Quant Harness解释完整量化应用：数据、计算、执行、报告和 UI/UX，以及它们如何共同约束研究范围、证据与接受条件。两者共享会话，不代表模型协议适配应该知道某个量化公式，也不代表“会话空闲”能够证明研究完成。两类文档分别落在 docs/agent-runtime/ 与 docs/quant-harness/；目录区分的是通用机制与完整应用，不宣称代码已经拆成独立发布包。

这次文档淘汰提醒我们：旧设计曾经正确，不代表旧目录和版本还应约束现在。值得留下的是选择依据，以及何时应该推翻它。如果未来上游运行时能承接现有分支、取消与报告契约，并实质降低长期维护成本，就应重新评估这条边界。保留自己的 Harness 是当前选择，不是需要捍卫的身份。

一次数据源故障，为什么需要三种成功定义

初稿 2026-10-12 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

一条用户反馈是这篇文章的起点：切换到 Tushare、保存 key 后，面板和状态栏没有同步，Agent 仍然报告 daily_basic 权限不足。用户的怀疑很直接：配置是不是根本没有改过来？

这条反馈暴露的不只是一条取数路径，还包括系统怎样向用户解释「成功」。

保存了数据源，为什么还不能确认它在工作？

配置保存、界面显示和工具执行，原本应该描述同一个应用状态。它们也确实各有职责：设置编辑器保存用户意图，面板投影状态，工具通过供应商接口取得数据。

但当三者给出相互矛盾的信号时，一条权限错误无法独立定位原因。可能没有读到新配置，可能端点仍然使用旧凭证，也可能配置已经生效，只是账户没有这项接口权限。仅凭这句话，既不能判定配置失败，也不能确认账号问题。

用户问「Source 和 Tool 是隔离的吗」，其实是在追问配置能否穿过我们的架构边界。职责可以分开，配置传播不能因此断开。

一个“成功”，承载了三个承诺

保存成功只证明某份设置已经提交。某次请求成功，只证明选定连接在那个市场、标的和窗口返回了有效样本。研究完成，还要求输入与任务范围、参数和计算方法匹配。

这些条件有关联，却没有替代关系：key 存在不能证明有接口权限，HTTP 200 不能证明有有效行，拿到价格也不能证明研究结论正确。

原来的紧凑快照路径还引入了一个不必要的条件：为了展示价格，调用了 daily_basic。于是，一项价格展示被绑定到更高权限的接口上。即使配置传播正确，用户仍可能失败；只修状态栏，并不能消除这项能力依赖。

而若让取数自动回退到别的供应商，再把原数据源标为可用，又会制造另一种误导：研究拿到了数据，却没有证明用户刚配置的连接能够工作。

连通配置，拆开保存、诊断与研究

WhyJ 在 runtime/data/source-runtime.ts 组装数据路径：读取设置、准备 provider 凭证、绑定缓存和归档，再调用 Source。Tool 负责模型可理解的输入输出，Source 负责标准化与回退，Storage 负责文件生命周期。Source 不必为了读取 key 反向依赖应用存储。

当前保存的配置覆盖相应环境值，显式调用选项通过端口传入，数据搜索也经过凭证加载入口。设置提交后的界面同步由 runtime 发布；设置来源与一次请求实际命中的 provider 仍须分开表达，后者可能经过回退。

快照工具则收缩了自己的承诺：复用 bars 的最新 OHLCV，不再为紧凑价格展示额外依赖 daily_basic。这同时意味着它不承诺 PE、PB 或市值。去掉一个权限依赖，并不是保留所有字段的免费优化。快照工具实现

图 2：共享 adapter，不共享成功标准。A/B 是示意 provider，不代表某次真实检查已经通过。

普通研究可以按允许的策略回退，并返回实际 provider 与日期；Doctor 则固定连接、单源和请求窗口，不读缓存、不跨 provider 回退，也不放宽窗口寻找旧数据。AKShare 的成功不能替 Tushare 的权限背书。

配置编辑也据此拆开：数据草稿先检查，再显式保存与检查证据匹配的版本；模型 Save & Verify 不顺带保存数据草稿。用户修改参数后，旧检查不能继续替新草稿背书。

动作可以宣布什么仍然不能宣布什么
保存这一版设置已提交所有相关接口都有权限
单源诊断指定请求取得了有效样本其他端点、日期、市场同样可用
研究验收显式条件已有匹配证据模型所有解释正确、策略能够盈利

少一个权限依赖，多一份判断责任

配置绑定、单源探测与草稿检查都有对应实现和回归入口。它们让「哪份设置被使用」「哪个请求得到什么证据」成为可检查的问题，但本次博客修订没有重新调用用户账户，不能据此宣布其 daily_basic 权限已经恢复。诊断契约与回归

现有 API 还留下一个不够直观的地方：envelope 的 ok、报告级 ready 或退出码可能只表示诊断报告生成完成。自动化消费者仍须读 overall 和各阶段状态，因此 ok: true 与 permission-denied 可以同时出现。拆开语义改善了可解释性，却也增加了消费端的判断责任，不能把它写成已经完美统一的接口。

取得数据之后，还有「究竟是哪一份」的问题。Bars 和基金 NAV 使用固定版本引用，研究重读指定 DatasetRef，缺档不拿最新缓存替换。但本地观测时间不是供应商发布时间，今天获取去年的数据，也不能证明去年当时已经知道这些数据。存储与时间边界

回头看，旧 Doctor 草图把配置、工具和数据放在一张诊断面板里，这个组织方式可以保留；把配置存在、流程结束和能力可用压成一个成功标签的判断，却必须纠正。验收单位因此从「接入 Tushare」缩小到「这份配置、这个端点、这个窗口的有效响应」。单源检查会暴露普通回退掩盖的失败，也让用户多做一步验证；这是为了获得可解释的失败归属而接受的成本。

重复面板草图不再保留，自动修复、后台巡检、全供应商扫描也没有因为出现在旧设想里就成为现有能力。后续若统一退出码与总体状态，必须同时迁移 CLI、面板和自动化消费者，不能只改一个绿色标签。

压缩对话之后，研究事实从哪里回来

初稿 2026-10-12 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

“继续刚才的比较。”对用户来说，这是一个自然的续问。对研究 Agent 来说，它要求找回的不只是一句话，还有那句话成立时的输入。

续问需要找回的，不只是一句话

早期 context 设计保留 last_symbol、最近工具和结果形状。这些线索很实用：它们能帮助理解「这只股票」「换个窗口」，避免用户每次重新描述对象。

而一项跨天继续、需要导出报告的研究，还依赖权重、币种、日期、基准、费用和数据版本。如果摘要记得「组合 A 优于 B」，却遗漏比较区间，那么语言是连贯的，研究依据却可能已经改变。

因此，问题不在于能否保存更多聊天记录，而在于：经过压缩以后，哪一部分信息仍然足以支持原来的判断？

最近发生的，不一定是最重要的

Anthropic 的上下文工程讨论强调有限注意力下的信息选择，Manus 则讨论借助外部存储恢复上下文。这些方法都提醒我们不必把一切塞回窗口；但对 WhyJ，保存一个路径或一句摘要仍不够，还要知道它对应哪份输入。Anthropic、Manus

项目里有一个更具体的反例：任务先由较早的回测满足条件，随后又执行八次不同本金的回测。任务仍显示 complete，模型上下文却只保留最近六次操作，原验收证据被挤掉了。

这次丢失并不完全来自摘要。选择规则把「最近发生」当成了「当前最重要」，因此即使摘要写得更好，也没有修复证据优先级的问题。反例与修订

旧 CLI 文档一度把 compact 描述为不消耗模型的启发式压缩，还把 slash 一概视作不触发模型的本地动作。两句话都越过了实际机制：当前压缩调用模型，显式模型诊断也会产生请求。因此淘汰的是这两项保证，而不是把它们换个说法继续归档成参考规范。轻量续问线索仍有价值，却不能因此升级成事实账本；用户需要在执行前知道压缩的延迟与用量，而非事后才发现成本。

让摘要和研究状态成为两种投影

当前会话 JSONL 是带 parentId 与 leaf 的追加树。压缩写入 compaction 记录，改变发给模型的消息视图，但原分支事件仍然保留。ResearchState 沿当前 leaf 的完整祖先链重建，不扫描其他分支，也不从压缩后的聊天文本倒推事实。

图 3：摘要维持交流，结构化状态恢复研究依据；两者消费同一历史，却承担不同保证。

一条模型文本说「最大回撤为 8%」，不会直接变成已核验发现。系统先配对调用与结果，检查工具名、调用 ID、参数及顺序，再读取固定数据，重算支持的指标。概念上：

研究状态 = 投影(
  当前分支的调用与结果,
  固定版本的公开观察,
  参数匹配与可支持的重算规则
)

投影区分 pending、failed、unverified、verified，也保留管理动作的 recorded。成功编辑观察组合可以被记录，但它并不因此成为投资结论。核验逻辑放在独立 research/，由会话和报告共用，避免两处「已核验」采用不同标准。

接着修正选择规则：先放入当前任务条件绑定的证据，再合并近期操作和未解决项；任务报告也优先于普通最近报告。达到预算上限时明确给出省略计数，而不是悄悄让上下文看起来完整。

恢复还要处理失效。如果原 DatasetRef 的归档丢失，系统保留范围与引用，但撤销相应核验发现；任务可能从 complete 回到 blocked。旧事件不改写，今天还能不能支持它，则重新判断。切换会话也先准备资源，再提交 leaf 和活动状态，准备失败时保留原会话。

恢复材料之后，问题还没有结束

已有恢复回归故意让摘要遗漏参数，检查下一次实际 Pi 请求仍包含重建字段；针对较早任务证据的回归，则验证它不会被后续无关回测挤掉。它们证明的是材料恢复和选择机制，不是模型解释已经获得普遍正确性。结构化任务与验收

我们为此承担了三类成本：模型压缩有延迟与用量，固定数据需要持续保留，研究投影需要匹配、重算和失效处理。当前预算还是数量与字符上限，不是精确 token 调度器；更长历史与更大组合的重算时延，也不能用「结构化」一词带过。

因此，对短问答，这套机制可能过重。对明天还要重新打开、说明输入来源的研究，单纯保存最终回复又明显不够。判断边界的方法不是问「需要多强的记忆」，而是问「恢复后必须重新证明什么」。

这也是本次淘汰旧 context 正文时留下的反思：不能因为旧方案更轻，就继续让它承担没有定义过的保证；也不能因为新方案更完整，就宣称记忆问题已经解决。下一步要测的是模型如何使用恢复材料，而不是再证明材料已经存在。

工具和 Skill 越多，Agent 就越强吗

初稿 2026-10-12 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

增加工具通常能扩大可做的事情。问题是，模型看见了一项能力，并不意味着当前环境能够执行它，也不意味着用户允许它在这次任务中执行。

模型应该看见哪些能力？

在工具较少时，一张 registry 很容易理解：名字对应 schema，schema 对应执行函数。再把 Skill 加入提示词，模型就有了怎样组合这些工具的说明。

随着研究范围扩展，这个起点开始遇到真实限制。数据工具依赖凭证和端点，脚本依赖 Python 与文件，Skill 还可能要求宿主根本没有的搜索或工作区能力。与此同时，用户只想完成一个有对象、有窗口、有边界的任务。

因此，我们需要回答的已不只是「仓库里有哪些工具」，而是「这一轮可以向模型承诺哪些能力」。

已经安装，却不一定可以调用

例如，工具可以注册成功，却因缺少 Python 无法运行；Skill 可以安装成功，却引用当前宿主没有的服务；某个动作在技术上可执行，却超出用户限定的对象。它们都可能表现为「Agent 不会用工具」，但继续修改同一段 prompt，不会同时解决这三种原因。

「清理无关 Skill」也有这种歧义。删除磁盘文件、关闭外部发现、精选默认入口、限制当前任务模式，是不同操作。若只看用户机器上是否存在某个目录，就把里面的全部指令加入研究能力，等于让安装环境替用户决定任务范围。

更隐蔽的冲突发生在资源更新时：新 Skill 已经进入索引，旧工具还在运行；或者任务排除了 bash，依赖 shell 的 Skill 仍被描述为可用。各份清单独立看都合理，组合起来却没有可执行的含义。

还有一次，用户已经给出研究材料，Skill 也选中了正确的 risk health 工作流，通用提示却继续要求先建立价格研究任务。模型于是填出空基准和并不存在的 supplied_snapshot_audit 验收工具。我们原先把统一的“价格→因子→风险”顺序当作质量保障，它却把材料解释挤进不相容的任务类型。错误不在工作流没有读到，而在宿主预先规定了所有研究都必须长成同一种形状。

资格检查本身也犯过类似错误：包元数据存在、版本满足，就被当成 Python 依赖可用。实际导入仍可能因 DLL 或传递依赖失败。2026-10-13 的回归把这个误判变成失败用例，之后才分开“版本已查”和“同一解释器确实导入成功”。这不是安装器更聪明就能代替的判断，因为安装事务与运行环境有不同的失效条件。

从工具清单到有条件的资源快照

WhyJ 分开维护四个判断：registry 说明工具是什么，readiness 说明已知依赖与限制，probe 提供指定端点和参数的观察，ResearchTask 声明这项工作允许使用什么。

图 4：可见资源限制与执行检查相互补充；就绪证据仍有范围，不能预判所有外部调用成功。

请求准备时，一个简化关系是：

业务工具集合 = 宿主活动工具 ∩ 任务允许工具
Skill 运行模式 = 这份工具集合与依赖证据能够支持的模式

这里有一个必须说清的例外：宿主若提供 research_task，它作为任务管理通道继续可见，不受业务工具白名单过滤；任务取消后也要保留它，才能声明新任务。管理事件仍有自己的校验，不等于绕过范围执行行情或交易。

只缩小可见集合还不够，所以执行前再次核对工具、对象和窗口。前一层减少无关选择，后一层处理模型仍提出越界动作的情况。两者都不构成第三方代码沙箱，宿主回调与扩展仍是受信任代码。任务装配与守卫

Skill 则按运行模式声明依赖。精选 catalog 固定来源版本，安装器检查本地修改、准备更新并在失败时保留已有内容；readiness 另行核对工具、解释器、文件闭包或有限网络观察。完整数据模式不可用时，用户提供证据的受限模式可能仍可用，但回答不能把后者描述为前者。安装契约、依赖契约

因此 --check 的版本与文件结果不再独自授予需要 Python 包的模式运行资格；显式 --check-imports 在同一实际解释器中加载声明的包。导入成功仍不能覆盖文件漂移、网络或授权。它增加了检查步骤，也意味着不同证据会各自过期，系统必须能够撤销曾经给出的资格。

扩展带来的 tools、skills、capabilities 共同进入带 revision 的资源快照，准备成功才提交，准备失败保留旧资源。在途循环和排队续问保持原快照；任务约束另生成请求级子集。

任务入口也因此改为先区分意图：需要受支持计算和固定数据验收时，读取真实 acceptanceTools 再声明；只是解释明确提供的材料时，保持 limited-evidence 边界，不编造一个核验器。已有任务不能被这种分流悄悄重置。代价是路由不再只有一条，而判断也仍可能失误；共享工具目录能消除虚构名称，却不能独自证明模型理解了用户。

Manus 讨论过工具定义变化对缓存与历史一致性的影响。这里借鉴的是对变更成本的警惕，不是复制其解码屏蔽机制；WhyJ 没有实现或测量同等的 KV-cache 收益。Manus 原文

少承诺一点，就要多维护一点

任务装配与守卫已有回归，固定 Skill 评测也保留了工作流选用、受限模式和回答错误的记录。它们能证明某个范围内资源一致、越界动作被拦截，不能证明工具集合变小后，所有研究都更快或更准确。Skill 评测及限制

代价是清单不再只维护一个函数名。固定版本、文件闭包、模式依赖与资源 revision 都需要更新；上游 Skill 变化时，旧检查可能不再适用。无法可靠确认的能力必须保留 unverified，这会比「全部 ready」显得保守。

图表技能的检查器也曾把合法的 PowerShell reference 读取挡住。修正允许的读取形态之后，还要区分“预览前 60 行”和“完整读完要求的三份 reference”；命令放行不是内容消费证据。这个反例提醒我们，检验器失配不能被归为技能本身失败，修好检验器也不能反过来证明任意 shell 已安全。

一次验证还提醒我们不要跨越环境边界：GitHub raw 下载超时后，隔离验证改用本地已有的同一固定 Git 对象，继续检查脚本与公开 CSV。缓存源码下的路径可以通过，但它既不证明 GitHub 已恢复，也不证明用户另一个 checkout 已就绪。当时的导入观察与缓存源码路径回执保留在本地输出；这不是把失败环境换掉以后，宣布原环境修好。

扩展分发也做了类似选择：WhyJ Extension API 1 用静态 import 显式加载，先验证独立扩展能够接入，再扩大分发范围。它更容易审查依赖，却没有直接安装 Pi 原生扩展的兼容性。扩展设计

这次整理撤下旧工具数量和重复注册说明，并不是因为数量毫无意义，而是它无法回答最重要的问题：模型被告知能做什么，这一轮实际又能做什么。后续若固定任务仍反复误选，就该调整工具粒度或说明；若失败来自缺依赖，就补依赖契约。继续增加注册项，不应该成为这两类问题的默认答案。

测试全绿，为什么仍然不能交付一个结论

初稿 2026-10-12 · 修订 2026-10-15 · oh-my-quant · Markdown 原文

2026-09-14 的核验记录里，有两个事实同时成立：调整后的项目测试 691 项通过；独立回测探针仍算出了错误权益。绿色结果没有撒谎，它只是没有检查这些数值契约。

什么证据足以支持一个研究结论？

测试首先帮助我们确认程序行为：参数校验、工具调用、状态提交和页面渲染是否符合预期。Agent 应用还需要确认外部请求是否可用、模型是否选择正确工具，以及最终文字是否忠实于结果。

这些工作都可以叫验证，但不能因此合成一张没有边界的成绩单。模型正常结束，不等于研究条件满足；研究条件满足，也不等于每个解释都正确。

技术负责人真正需要知道的是：某个通过标记排除了哪类错误，又留下了什么未知？

绿色勾选之外，反例依然存在

那次回测探针采用零费用、价格 100 → 100 → 110、本金 100000 的简单输入。1000 股涨到 110，应得到 110000，函数却返回约 111000。另一个 +10% / −10% 的探针，累计收益约为 −1%，CAGR 却是 0。这里保留的是 2026-09-14 的失败观察，不是本轮重跑结果；旧汇编已删除，现行口径和可重复反例分别进入计算契约与独立账本测试。

这些反例不因为测试通过就消失。它们说明已有断言没有覆盖正确的账本和年化口径，而不是测试数量不够大。文档也曾沿用“初始名义本金且无现金约束”和统一 252/N 的年化简式；后来的实现已经采用现金、仓位账本与实际日历跨度，文字却没有同步。保留旧公式作为另一份规范，会让修过的错误重新进入读者的实现。

同类误判在回答层再次出现。2026-10-13 的一份对冲回答通过了当时九项自动检查，却把市值 9,240 相对成本 10,000 的亏损写成 240 / 2.4%；应为 760 / 7.6%。期限与预算单位检查改好了，并没有顺带证明情景算术正确。本地原始回执保留旧的 9/9 和错误原文；它是内部历史样本，不是当前通过率或默认公开素材。

新闻评测则暴露另一层问题：引用 token 合法，句子的数字却来自其他段落；工具返回「复权口径未知」，回答却将其写成「未复权价格」。这一次，数据链路和输出格式可能都正确，错误发生在解释承诺上。

因子回归提醒我们，样本形状也会制造安全感。旧 RSI 递推重复消费了播种期末的变化，后续输出延迟一条；持续上涨时两版都可能是 100，错误藏住了。换成收盘 [10,11,12,11,10]、周期 2，正确末两项为 50、25，旧实现却是 100、50。SMA 差的另一处错误则把未形成的短均线当作零，短周期出现伪造的 −100%。增加更多单调样本不会替代这些转折和暖机反例。

评分解释也曾把 RSI 的贡献 16.00 写成最大，同表 IV rank 却为 19.50。原始分数最高和加权贡献最大被混为一谈；总分正确，并不能让这个解释自动正确。原始套件保留当时回答，本文不回写它。

项目还曾因默认测试发现范围过宽，混入参考仓库的 Vitest 测试和生成 Artifact 的演示脚本。于是连「哪些失败属于本项目回归」都不够清晰。先定义测试集合，再定义各层通过意味着什么，成为改进的前置条件。

把反例变成下一轮检查

测试围栏把默认发现根限制在 src，排除 gen-*.test.ts，演示生成器改用显式入口。bun run test 先检查围栏，再运行项目测试。它稳定了工程回归集合，却不是禁止一切网络和写入的沙箱；副作用仍需由 fixture 与测试设计约束。

图 5：每层验证支持不同声明；反例回流形成迭代，不是层层通过就得到普遍正确性的阶梯。

证据可以检查什么不能替代什么
确定性工程回归参数、取消、分支、账本、渲染真实模型与供应商行为
真实服务样本选定连接、端点和窗口的响应长期稳定性与其他权限
固定任务轨迹工具、参数、调用顺序、恢复取数回答是否忠实解释结果
回答主张核对已知数值、口径、引用与条件错误未覆盖表达的人工判断

数值回归使用独立现金与股数账本，而不调用被测函数给自己生成期望值。在已定义的成交价格约定下，至少核对：

cash[t] = cash[t-1] - tradeShares[t] × price[t] - cost[t]
equity[t] = cash[t] + positionShares[t] × price[t]

这些不变量可以检出一类实现错误，但不自动覆盖真实成交、停牌、滑点与复权规则。独立账本测试

六因子随后采用独立计算的 Latest 期望和末次下跌路径，每个验收条件绑定自己的调用、周期与窗口。旧 RSI 归档不重写；如果按修正后的公式无法重现，就撤销核验资格。这个选择牺牲了旧报告持续显示 verified 的便利，却避免把兼容性变成继续承认错误的理由。因子方法与反例

显式评分则把用户给定的分数和权重交给无 IO 的算术工具，返回贡献、合计与并列最大项。它解决了这一层相乘与排名，不验证原指标怎样映射成分数，也不把高分解释为反转概率。评分契约

回答层则从已经观察到的错误建立规则。2026-10-12 的新闻迭代增加明确口径断言检查，并在证据可匹配时识别已知冲突。交互 AppRuntime 保留错误原文、追加复核提示，并阻止本轮自动报告继续生成，而不是把错误悄悄改成一份看似干净的报告。回答证据与门槛

这还要求检查器接受反例。限定语和否定句曾被当成正面断言；离线修改规则后，旧回答不再触发告警，只能说明重检结果改变，不能把原来的失败回执改成一次新的模型成功。反过来，引用格式有效、九项检查齐全，也不能抵消一句错误的数字解释。年报、基金比较与因子年化各有证据条件，不能共用一个没有任务边界的“回答正确”标记。

对那份对冲错算，后续实现增加了无 IO 的持仓情景计算，并将有限情景检查绑定到显式股数、成本与收盘价。旧错句成为回归输入；检查只覆盖识别到的未对冲股票情景，不核验期权收益或任意自由文本。后续模型样本的股票算术正确，仍出现“protective put 的保费最高”这类缺少同条件报价支持的比较。旧失败、离线重检和新样本分别保留在本地阶段回执，本文没有重新执行这些验证，也不把修好算术写成完整解释验收。

Langfuse 的 Skill 评测文章把输入、轨迹、评分与迭代连接起来。我们采用的是让观测服务于可重复改进的思路；当前仍使用本地事件和评测回执，没有因为引用它就接入 Langfuse 服务。Evaluating AI Agent Skills

修复一个错误，不等于得到总体正确率

回测权益和 CAGR 后续已有独立账本修复与回归，新闻检查也能拦截已知口径冲突。它们分别改善了确定的数值契约和有限的回答门槛，不应被合并为「研究质量全面提升」的数字。当前怎样复验，由统一评测指南维护；本文记录的是这些规则为何出现，不充当完整验收报告。

代价是验证本身也需要版本和边界。词法规则可能漏掉语言改写，合法引用不能证明句子与段落语义一致，人工审阅仍要发现新的错误类别。一次真实模型复测通过，也不能推出总体错误率下降了多少。

六因子的真实运行就是这个区别：数值已经正确，表头、中文逗号和编号标题仍使有限解析器误判；调整解析器后离线重读原文，只能更新重审结论，不能制造一次新的模型通过。同时，回答仍可能把均线差说成斜率，或对极小样本给出过强解释。源码快照与人工审阅分别留在本地修订记录和回答复核；旧 33 场景与新增后的 34 场景也不能拼接为同一总体成功率。

因此，一份回执要留下任务、输入、真实或合成环境、检查规则版本、失败回答位置，以及未验证项。成功率的分母也要固定：返回文字、完成工具、满足任务条件、人工确认解释正确，不是同一个事件。

文档清理在这里有一条硬边界：旧汇编可以删除，错误不能被改写成成功。我们把有解释力的失败与修正写进本文，把可重复输入放在测试、原始回执留在内部输出；没有把每次测试数量和运行日志重新搬成一本博客附录。代价是本文不再提供逐次运行的完整历史，追溯个别数字仍需对应原始回执。

工程回归本身也会偷带本机假设。2026-10-15 整理测试入口时，本地全量通过，但干净 Windows CI暴露 Doctor JSON 的「提示必须为空」依赖预装 AKShare。后来把测试改为显式缺 Python，断言 Tools 失败原因与结构化回执，而不把联网跳过误当依赖已经就绪。同期首个同步子进程返回空退出状态：最初怀疑工作目录，固定入口后全量仍复现、单组却通过。这份反例没有证明 Bun 的具体根因；测试改为等待实际退出并读完输出，仍检查退出码和原 JSON 契约。入口回归维护可重复条件，完整发布门槛与最终提交 CI 仍须分别通过，不能把单组成功外推成整库成功。

对下一笔工程投入，我们更愿意从反例出发。缺数据就修数据链路，误读口径就改证据与解释检查，调用越界就审查资源装配。测试的价值不仅是让发布前多一个勾选，还在于让「下一步改哪里」有具体依据。

终端为什么也是一个一致性系统

初稿 2026-10-12 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

一个面板可以画得完全正确，却显示属于上一次输入的数据。对研究终端来说，排版只解决了「怎样看见」，还要解决「此刻看见的是什么」。

旧结果还有没有发布资格？

模型研究可以持续很久，行情 Overview 则需要独立更新。用户不应该因为模型正在回答，就无法刷新观察组合；也不应该因为行情刷新，正在进行的研究就被切换到另一套输入。

自定义 frame-buffer 给 WhyJ 提供了布局和输出控制，但它不会自动解决这些关系。屏幕需要知道一份结果属于哪个组合、哪轮请求，是否仍有发布资格。

因此，我们把终端问题从「如何更快地画一帧」向前移了一步：先确定这一帧有权表达哪些状态。

稳定的画面，也可能掩盖错误的时间

假设用户切换组合，新请求先完成，旧请求后完成。若按最后返回者覆盖，界面会跳回旧组合。即使调用了 abort，某个客户端或脚本也未必立刻停止，旧 Promise 仍可能返回。

另一个冲突来自渐进刷新：本轮只收到几个标的，其余行沿用旧价格，却共同显示刚更新的时间。面板更完整了，数据却来自不同轮次；用户无法分辨哪些内容仍然有效。

等待全部结果可以回避这种混合，却会让一个慢请求拖住整个面板。保留所有旧值可以减少空白，却可能让视觉连续性替数据新鲜度作了保证。这两种体验目标不能仅靠更快的渲染同时满足。

旧布局稿主要描述窗口、行数和区域。它保留了视觉意图，但不能继续作为这些异步行为的完整规范；像素式尺寸也无法替代终端 cell 与中文显示宽度。

先确定归属，再决定怎样绘制

OverviewRefresh 单独管理刷新请求、周期、取消与发布，模型研究使用自己的生命周期。AppRuntime 连接用户动作与这两类操作，TUI 只消费状态投影。

每轮刷新带有 generation。新输入使旧轮失效，发布前再次核对轮次、取消状态与截止时间。取消用于减少无用工作，代次检查用于拒绝迟到结果，不能因为做了前者就省略后者。

图 6：示意新轮取得可用行的分支；首个返回若是无数据行，也会发布进度。取消与代次检查各有职责，时间间距不表示实测延迟。

请求池对本轮规范化标的去重并限制并发；首个请求行返回后开始发布，它也可能是一行无数据结果，后续返回再短时间合并重绘。一旦进入本轮画面，尚未返回的行显示 --，不从上一轮补价格。

刷新尚无返回行时，旧面板标为「上次结果」；若失败或超时仍未取得本轮返回行，则以 stale 保留旧面板。全部请求返回但无可用报价时，表达的是本轮 unavailable，而非恢复一整块旧报价。进度出现与首份可用报价到达，因此也是两个不同时间。

每行还保留实际 provider 和数据日期。本地刷新完成、最后交易或净值日期、供应商发布时间不能合成一个时间戳。截止时间使用单调时钟检查，但仍不能抢占任意同步 JavaScript；这是协作式取消，不是严格实时系统承诺。

输出流的规则则不同。Screen 等待 drain 时只保留最新待发帧，恢复后重画同步画面；中间动画可以合并，研究事件仍由会话账本保存。展示需要及时，日志需要完整，因此不应共用同一种队列策略。

Settings 也按状态归属处理：模型保存不附带行情请求，数据验证后保存刷新一次，退出父面板不重复刷新。草稿改动使旧检查失效，面板关闭使迟到回调失去发布资格。这些规则与研究分支的提交边界，是同一个问题在界面侧的体现。

让不完整可见，并没有免除性能责任

当前刷新、设置冲突与退出清理都有对应回归，测量记录也区分首个可用结果与整轮完成。它们为迟到覆盖、草稿串用和输出清理提供检查入口，不等于所有真实终端、供应商和输入法都已验证。当前复验入口见数据评测与文末测试，不把它们称作本轮运行结果。

用户会更容易看见 --、partial 与 stale，这是我们接受的代价。它暴露了取数的不完整，没有让流畅画面替后台作保证。但如果缺项持续很久，界面诚实并不能免除我们优化供应商、并发和超时策略的责任。

frame-buffer 的维护账也仍然存在：中文宽字符、焦点、裁剪、备用屏幕清理和多尺寸布局都由项目承担。stdout 的 drain 只表示流恢复容量，firstResultMs 只表示运行时发布了首份报价，两者都不是用户已经看见的时间。

因此，这次文档整理把旧窗口尺寸和重复命令表交还代码与专门参考，把代次、时间、焦点和失败语义留下。终端方案的演进换成 Web UI 时，这些约束仍然成立；可以淘汰的是布局实现，不能顺带淘汰的是状态归属。

报告要固定，设计要演进：我们保留什么、淘汰什么

初稿 2026-10-12 · 修订 2026-10-14 · oh-my-quant · Markdown 原文

研究报告需要保留当时的输入，设计文档却需要跟随实现变化。如果对两者都采用「全部原样留下」的策略，我们可能保存了更多文件，却更难回答哪份内容今天仍然有效。

可追溯，究竟要求我们保留什么？

WhyJ 最初面对的是报告问题：用户重新打开昨天的研究，应该看到昨天那份结果，而不是用今天修订过的行情重新画出的同名页面。研究过程和来源需要留下，后续才能恢复、核验和讨论。

整理项目文档时，我们采用过类似的谨慎做法。2026-10-12 先收敛当前设计，同时保留长篇原稿和旧入口，避免丢失尚未提交的内容。这保护了材料，也为之后复核提供了依据。

但报告和设计的有效性不同。报告需要固定一次观察；设计需要说明当前契约。保留历史很重要，却不能让历史继续拥有现行规范的地位。

文件还在，有效性却已经改变

对报告而言，HTML 存在，不代表原 DatasetRef 还可读取；一份报告可以正常打开，却已经无法重算其中的指标。完整聊天记录也可能包含用户输入、资金金额与本地路径，不能因为生成成功就直接公开。

对文档而言，问题更像是多份版本同时发声。旧 Artifact 稿提出独立 recorder、.traj.jsonl、plan/decision 事件、DAG 与 replay；当前实现却从 session 分支派生轨迹。如果两者都以详细设计的形式出现，读者就要自行猜测哪些是计划、哪些已经落地。

这次清理还发现，两份标为早期和最新的 GOALS 在统一换行、去掉首尾空白后内容相同。旧核验说明却写着后一份新增了刷新、分类与 slides。这个判断没有文本差异依据，不能继续解释为一次需求升级。文件保存得完整，并没有阻止我们对它们之间的关系作出错误解释。

原输入里的 yhoo 也只能标为暂按 Yahoo 理解，后续明确的选择是不强制该来源；“三类”只命名了 Harness 与 UI/UX，“产品与交付”是编辑分类，不是用户追加的功能。实盘诉求则保留为需求，本阶段仍只留文档与接口，不据此取得真实账户下单授权。合并可以改变组织方式，不能补写不存在的用户决定。

所以，问题不只是保留多少，而是保留什么身份、证据和有效期。副本更多，不会自动带来更清楚的历史。

固定研究事实，让设计继续演进

报告固定版本，不固定今天的核验判断

当前 Artifact 保存 HTML、元数据与 provenance 的不可变版本。用户选择 id@revision，打开的是那份保存的字节。恢复则另外核对源 entries、顺序、leaf/parent 与内容指纹，准备成功再切换分支。

Trajectory 也复用选定 session 分支，不另建一套实时 DAG 账本。它减少了两份记录的身份与顺序协调，代价是只能展示实际捕获的事件，不能补出未记录的决策，也不能承诺任意执行重放。真实多 Agent 或跨进程因果需求若超出现有分支表达，再重新评估 recorder，而不是把旧草图自动转成待办。

淘汰 recorder 方案时，不能连它的采集边界一起删掉：可审计事件、可展示的推理摘要，不等于模型底层隐藏思维链原文；拟新增的采集器也不应记录系统提示、密钥或认证材料。这是约束，不是对现有报告过滤效果的追认。当前完整报告从会话派生，仍可能含用户原文、模型输入及可见 thinking/compact 记录，应视为私有产物。

文档保留理由，不继续保留重复规范

我们的第一次收敛并不彻底：先分类、保留路径，再将旧稿汇成 13 份主题归档，另设一份设计决策账。顶层入口少了，阅读负担却被移进归档；读者依然要在规范、历史汇编、决策账和博客之间拼出“现在相信什么”。把“没有丢文件”当成“文档已经整理好”，是这轮工作本身需要纠正的判断。

因此，2026-10-13 的下一步不再是继续归档：删除主题归档、归档索引和独立决策账。现行 Docs 说明现在怎样使用、实现和验证；PRD 维护范围与状态；Blog 直接承接错误判断、修正理由、代价及重审条件。旧测试数量、重复命令表、生态全目录和中间验收流水不再复制。仍有必要保留的原始运行输出留在内部证据位置，不作为网站内容自动发布。

但这一步仍没有完成整理。research-* 把任务、状态与宿主端口分散解释，skill-* 又让安装、发现、资格和输入各占一页；只是删掉 archive，读者仍要自己拼出完整生命周期。任务 ID 一处写成必填，另一处已经允许首次声明由宿主补齐，就是拆散维护带来的具体冲突。这轮继续把 16 份相关文档收敛到 Harness、Skills、量化工具、数据源和 UI/UX 五个主入口，删除被吸收的 11 份，不留下跳转壳。

合并的单位因此改为责任和读者任务，而不是文件名前缀。研究日线的来源/时间证据归数据源，价量公式归量化工具；二者用链接明确交界，不能因为都叫 research 就混成同一种保证。代价是主文档会更长、旧外链失效，收益目前只能说是减少重复规范和定位歧义，尚不能宣称读者理解更快。

第三方 Skill 目录也不值得再复制一遍。上游维护功能与工作流，我们维护固定版本、安装/发现、资格和证据边界；详细案例回到可执行的本地注册表，功能介绍只保留上游 URL。删除说明副本不等于卸载运行依赖，更不能把用于复现错误的测试 Skill 夹具一起删掉。

同样的分歧后来出现在验证脚本里：一次修复需要固定日期、固定端点与本机条件来形成证据，但这些条件不必永久成为日常入口。早期 Pi 双 CLI 探针只接受输出路径，文档却把它写成能选择连接、查看帮助的通用检查；图表生成器则依赖个人 Skill checkout 和本机字体。文件存在，不代表验证方法已经可移植。2026-10-14 的清理因此删除六个重复或旧环境绑定的入口，保留具有独立范围的测量、证据重算和确定性反例，现行复验方式明确各自能证明什么。代价也要承认：新的 source 测量并不原样复跑旧「固定端点 + 编译 CLI」探针，单侧 Doctor 不证明双 CLI 并发；原场景需要从对应 Git 版本复现。减少文件只是结果，避免替代入口悄悄扩大自己的证明范围才是这次收敛的目的。

脚本迁移也不能只按它调用了哪个模块来分类。终端刷新探针需要跨越数据编排和绘制，若移动后直接套用生产依赖规则，它会被误判为架构倒置；若放宽整个模块，又会让探针成为生产依赖的后门。我们的选择是模块内 dev/ 承接显式开发入口，根目录 tests/ 承接跨模块回归，npm 命令负责统一调度。生产文件仍不得导入 dev 或测试代码，构建闭包还要独立确认这些代码没有进入 CLI。代价是现在必须维护两类消费者和两个测试根，而不是假设一张目录图就能同时代表生产、开发与验收。移动文件改变归属，不改变旧证据的证明范围。

接下来的一次分类仍然偏窄：我们把 Quant Harness 几乎等同于任务守卫和证据核验，再把数据、计算、执行和 UI/UX 并列放在外面。这个边界能描述某个源文件，却不足以描述产品。用户选择数据、等待计算、理解失败、恢复报告的整条路径，正是量化应用必须提供的运行环境；UI 不是事后包装，数据和计算也不是附录。

因此，2026-10-14 的调整真正落到了目录：docs/agent-runtime/ 保存通用运行机制，docs/quant-harness/ 保存完整量化应用及其内部设计，原来的顶层文件实际迁移进去。只在索引里分两组标题并没有完成这件事。模型设置、诊断、测速仍各有唯一正文，产品模块也继续保持依赖边界；改变的是文档的应用归属，不是把所有代码装进同一个模块。

这需要同步修改文档交叉链接、源码中的使用提示、测试读取路径和官网入口。迁移增加一次可见的维护成本，换来目录树与产品范围一致；目前可以检查的是文件归属和链接有效性，还不能据此声称读者理解更快。

系列保留十二篇机制图与实现入口，并通过构建和链接检查约束导航。它们可以检查整理后有没有缺文件、断链接和重复入口，却不能证明 Agent 因而少犯了多少错误；我们没有做这样的效果测量。

研究终端，为什么不能只是一个聊天框？

初稿 2026-10-13 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

用户今天比较两组标的，明天再问“换一个基准会怎样”。对话可以接着说，但研究是否真的接得上？这个差别决定了 oh-my-quant 应该围绕消息设计，还是围绕持续进行的工作设计。

用户离开以后，什么应该留下？

聊天是一个合适的研究入口。用户不必先理解因子函数或工具参数，就能提出一个尚不完整的问题，再通过追问补齐日期、对象和比较口径。自然语言承担探索，而不是要求用户在第一步就填完所有表格。

但用户离开之后，需要留下的不只是一段回答。下一次研究还需要知道：比较了哪两组标的，采用什么日期、权重、币种和基准，当时的数据是否仍然可核验。这些信息如果只能从聊天文字中重新猜测，连续对话就不等于连续研究。

PRD因此把主要工作串成“配置 → 获取数据 → 分析与比较 → 报告 → 恢复”。从产品设计看，这条链比功能清单更有约束力：报告不是最后多一个导出按钮，而是下一次研究的入口。

功能都在，工作仍可能接不上

已有的终端验收记录提供了一条很具体的路径：在界面开启自动报告，创建两组观察标的，输入带日期、基准和币种的比较请求，完成计算，再通过 /clear 重置当前研究会话（保留磁盘存档），从报告恢复。测试必须经过这些入口，而不能直接调用比较函数代替用户完成工作。键盘流程回归保留这条可重复路径。

这里有一个容易被功能统计掩盖的冲突：单独的“创建组合”“运行工具”“生成 HTML”都能成功，组合起来仍可能丢失来源会话，或者在恢复时重新取一份不同的数据。局部能力存在，并没有回答用户是否能够接着昨天的工作往下做。

对象名称也会改变承诺。Portfolio 听起来像一个账户，但默认 Portfolio 管理的是观察标的与分组，不持有用户的实际股数、成本或现金。把它展示成“我的资产”，会让公开行情与模拟结果承担并不存在的账户含义。这个限制不应只藏在技术文档里，而应进入帮助、字段和报告用语。

把探索、控制和留存放在不同位置

当前产品把自然语言交给研究过程，把配置、诊断、组合维护和恢复交给明确的本地入口。Analyzing 展示研究，Overview 提供观察背景，Composer 承接意图，报告保存一次有来源的结果。它们服务同一条工作流，却不要求用户在同一个聊天流里完成所有事情。

图 8：产品工作流示意，不是逐屏操作截图。箭头表示工作如何延续；报告可打开、来源可恢复、证据可重算仍须分别检查。

这一选择也可以放在三种产品组织方式之间理解。下表是对当前方案的分析，不是对历史方案会议的还原。

组织方式对用户的帮助留下的成本

因此，“少几个页面”并不是这里唯一的简化标准。更重要的是用户是否还需要反复搬运同一份参数，是否知道下一步在研究、修改设置，还是恢复一份旧结果。第 11 篇讨论这些入口怎样被发现，第 12 篇讨论它们失败后怎样继续。

实盘执行没有被塞进这条默认研究链。研究完成不能继承下单授权，真实账户业绩也不能由观察组合估算。执行端口与私有账户输入各有独立契约；这缩小了默认产品的承诺，也意味着用户不能把它当作完整交易工作站。执行边界、账户业绩

模块拆开以后，为什么还需要一层 Runtime？

初稿 2026-10-13 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

把取数、存储、计算和终端分到不同目录，只完成了架构工作的第一步。真正的考验是：换一个供应商、接一个工具，或者改变一种展示，究竟需要哪些模块一起修改？

我们想让哪一种变化停在边界内？

第 01 篇讨论 Pi 与自有 Harness 的分工。这一篇向应用内部看：Source、Storage、Tools、Runtime 和 TUI 为什么不能简单合成一个“数据服务”？

它们确实处理同一项研究，但变化原因不同。供应商字段和回退策略属于 Source；文件路径、缓存修订与提交属于 Storage；一个因子的公式属于 Quant；输入焦点和可见行数属于 TUI。把这些变化分开，才有机会在换取数方式时保留计算，在换展示时保留研究结果。

目标不是让模块彼此不知道对方存在，而是让依赖必须经过可解释的入口。用户最初问“Source 和 tool 是隔离的吗”，也可以从这里回答：它们有职责边界，但工具仍需通过应用组装的数据入口取得配置、数据与来源；隔离不是各自维护一套配置。

直接调用很短，隐含依赖却会变长

一个方便的实现是让 Source 自己读取本地配置和缓存。另一个方便的实现是让 TUI 在需要报价时直接调用 provider。每条路径都很短，但它们会把宿主选择藏进较低层：取数模块开始知道 .ohquant，界面开始决定回退和错误分类。

当前源码采用了相反的约束：Source 和 Storage 不互相导入，TUI 不直接调用 provider，session.ts 不直接导入 Storage、Tools、Source 或 TUI。这些是架构检查中的具体规则，不只是模块图上的理想箭头。

规则本身仍不够。如果一次只读历史归档的请求，也必须先加载当前供应商的凭证，它虽然没有违反目录规则，却仍把两种生命周期绑在了一起。接口存在只是起点；数据路径是否会被无关的配置阻断，才是边界需要回答的具体问题。

在组装点连接，在计算和渲染前收敛

以需要可归档日线的研究调用为例，Tools 经 runtime/data/source-runtime 调用 Source。Runtime 注入设置与凭证读取、缓存、归档读取和保存钩子；Source 负责供应商选择、标准化与回退，Storage 负责本地数据版本。这条路径不是所有数据入口的统一通道：Overview 和单源诊断有各自的时效与隔离要求。

图 9：研究日线调用与应用组装示意，箭头不是独立服务或部署单元。Source 通过注入钩子使用存储能力，不反向导入 Storage；并非所有工具都经过日线入口。

当前 createStorageSourceRuntimeDeps() 的内容很朴素：把 loadCachedBars、loadArchivedBarsBefore、saveBars 和来源偏好读取绑定给 Source。它之所以单独存在，不是为了多一层命名，而是为了让“怎样取得数据”与“本地宿主怎样保存数据”可以分别测试。

历史观察截止是一个更具体的分叉：带 observedBefore 的归档读取不需要供应商，当前 Runtime 保留存储依赖注入，但不为该路径附加默认供应商请求预算或凭证加载器；未显式指定来源时，仍需读取来源偏好。普通请求才绑定默认请求预算与延迟凭证读取。数据仍来自同一个 Source 门面，但不同请求不必承担相同的外部依赖，也不能把不调用供应商误解为完全不读取设置。取数组装实现

Session 同样使用显式宿主端口；完整注入后不隐式加载默认本地组装。这部分独立宿主与连接快照的验证已在第 01 篇展开，这里不把它当成另一套架构重新讲述。

纯计算与报告渲染也不是第二套业务判断中心。Quant 接收数据和参数；Research 核对归档及计算依据；Agent 恢复和 Artifact 使用共享核验逻辑，渲染器再消费准备好的结果。这样，一个来源缺失的判断不必在聊天上下文和 HTML 中各实现一次。

可替换不是免费的抽象

现有 Source Runtime 回归覆盖设置中的凭证进入请求、异步设置读取响应取消，以及调用者可缩短但不能随意放大默认预算；还以显式来源和注入 adapter 检查坏供应商配置下的旧缓存读取。这些是具体输入下的依赖与失败契约，不证明所有来源已经可互换，也不证明未来 Web 或远程宿主无需适配。本轮核读代码与原有证据，没有重新调用供应商或运行产品测试。

代价同样具体。Runtime 要维护转换、组装和生命周期，端口要处理空集合、快照、取消与准备失败；一次端口变更可能同时影响默认工厂、独立宿主和测试替身。这不是免费获得的“解耦”。

Runtime 也有变成杂物层的风险。当前的判断方法是继续按变化来源检查：如果某段逻辑决定供应商字段，应回 Source；决定持久化提交，应回 Storage；只是连接这些能力，才留在组装层。出现稳定、独立的生命周期，再考虑抽成专门服务，而不是看到文件变长就切成任意碎片。

Alpha/AKQuant 的旧 roadmap 还留下另一种错误：早期“尚未接入”的盘点被后续文档沿用，而工作区已经存在 Alpha 模块与 Python 适配。我们纠正了现状，却没有顺势把接入写成完整验收。保留的是固定输入、成本、窗口、引擎版本和失败语义；暂不为只有一个实际实现的场景建设通用引擎平台。第二个真实引擎若暴露稳定共性，再扩大协议，代价是届时可能需要迁移第一版适配。当前 Alpha 契约

反过来，独立模块已能构建，也不能证明默认 Agent 能用到它。Alpha 需要进一步检查注册表、缺依赖时的前置失败、固定数据归档和恢复链路。集成探针第一次还因为把报告的 metadata.path 写成 metadata.filePath 而失败；这要求修正检查器，不应顺手归因于引擎。扩展接入则曾因异步启动吞掉配置修复后紧接的输入，修复点是等待启动完成后提交，而非再加一层模块接口。这些具体失败提醒我们，可替换性与用户路径可达必须分别验证。

80×24 的屏幕里，什么值得一直留下？

初稿 2026-10-13 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

研究终端希望同时展示回答、行情、来源、模型状态和输入。每一项都有道理，但它们不能同时拥有最高优先级。窗口变小时，布局必须替产品作出选择。

每多留一行，就少读一行什么？

Analyzing 是主要工作区域，Overview 提供市场背景，Composer 保留输入，底部状态帮助用户判断当前连接。固定位置能形成稳定的操作预期，但固定区域越多，真正可阅读的研究内容就越少。

这不是把字号缩小就能解决的问题。终端按字符单元格布局，字体与真实字号由用户的终端控制。DESIGN中的字体、像素间距和圆角可以作为品牌与 Web 产物的参考，不能把 16px 正文或圆角卡片照搬成 TUI 已经实现的能力。

因此，终端里的留白需要换一种语言：少占几行装饰，给字段和操作分配稳定区域，让长中文按实际显示宽度换行。它首先是一份空间预算，然后才是视觉风格。

稀疏的画面，也可能只是高度算错了

2026-09-15 的小屏审计发现，60×20 中带完整预览的会话列表只能看到两行，报告列表只能看到四行。原因不是内容太多，而是从已扣过顶部区域的 contentH 中再次扣除了元信息高度。界面看起来不拥挤，却浪费了本来可以用于阅读的位置。

同一次复核还发现，空报告列表把整句下一步指引放在单行页脚，窄屏只剩前半句。这个“简洁”让用户失去了行动信息。Settings 没有常驻操作提示，进入编辑后还需要凭经验猜测怎样保存或退出。这些问题对应的小屏回归继续留在代码中。

这些反例使“Whitespace first”不能被解释为尽量空。需要保留的是能帮助用户理解分组和层级的空白，而不是由重复扣高、无效装饰或截断造成的空白。

先分配注意力，再分配颜色

当前主布局在宽度不足 78 列时隐藏 Overview，研究区域扩展；用户也可以在设置中主动关闭它。这里接受了一个损失：小屏不再持续显示旁侧行情。换来的是研究和输入保持可用，而不是两块区域都缩到难以阅读。78 列是当前实现阈值，不是对所有终端都最优的结论。

图 10：布局优先级与颜色含义的教学示意，不是等比例终端截图。实际布局由字符单元格计算；颜色之外仍需符号和文字。

面板也按信息职责分配区域：空态指引进入可换行正文，页脚保留数量或状态；列表按真实起点到底边计算容量；Settings 为字段、草稿、操作和错误各自留位。错误出现后仍能看到所改字段和输入，而不是让错误文本挤掉操作对象。

渲染方案本身也做过一次收缩：早期草案同时设想独立 renderer 包、制品 schema、主题层和 MCP render 工具，而当时真正缺少的是让模型保留结构化行。现有 Session 注入和文本 parser 已能承接表格、sparkline 与对比块，因此先复用这条链，把行为纳入 UI/UX 契约。我们放弃的是没有当前需求支撑的子系统，不是丰富交互本身；代价是只能识别有限文本形状，任意 JSON 不会自动变成可交互图表。

多显示几行，不等于已经更好用

相同数据下，60×20 会话列表的可见行数由 2 增至 5，报告列表由 4 增至 8。这是历史审计中的布局修复结果，不能改写为“阅读效率提升一倍”。相关回归检查不同尺寸、中文列表、错误输入保留和末项选择；字符网格投影也接受过浏览器视觉复核；本轮没有重做浏览器或物理终端检查。

截至 2026-10-09，本地布局流程与语义色范围已验收；目标终端的字形、输入法、最终像素仍是另一层检查。更没有证据表明某套颜色已经适合所有用户：保留符号是避免只靠颜色传意的约束，不等于做完了完整无障碍评估。

接下来值得观察的不是用户是否觉得画面“高级”，而是他们能否分清待取数与零涨跌，能否发现焦点，是否因隐藏 Overview 而频繁往返查看。布局优化应减少任务中的辨认和切换成本；如果只是让截图更满或更空，都还不足以支持设计结论。

用户不知道下一条命令时，界面应该做什么？

初稿 2026-10-13 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

熟练用户记得命令，初次使用者只知道要做什么。同一个终端要同时服务两者：既不能让每次操作都经过向导，也不能要求用户先背下完整手册。

能被调用，不代表能被发现

自然语言让研究入口更开放，但不会自动解释应用的全部操作。用户仍需要知道怎样配置、查看诊断、维护观察组合、找回报告。把这些动作全部交给模型推测，会让本应明确的本地控制变成一次不确定的对话。

当前产品保留十个公开 slash 入口。名称优先使用 /config、/resume、/help 等可识别动作，描述再说明研究对象；业务分析经 Agent 工具完成，没有为每个因子或比较再增加一条顶层命令。命令参考维护现行行为。

这是对入口数量的控制，却还没有解决“下一步在哪里”。一个未知命令如果只返回 unknown，用户仍需要离开当前任务找文档；一个空列表如果只显示 empty，也没有告诉用户如何获得第一份结果。

帮助可能看不全，甚至会执行动作

早期 Help 把命令和快捷键并排显示，在 60×20 中把说明截为 Compact resear… 和 Ope…，80×24 也存在截断。屏幕里信息很多，但用户无法仅凭完整句子判断动作。

更严重的反例出现在分派：某些 --help 参数会被忽略，/clear --help 仍重置会话，/compact --help 仍进入压缩。用户本来想降低不确定性，查询却先改变了状态。帮助不是额外补几段文字的问题，而是入口执行顺序的问题。

这些发现改变了验收重点：不仅检查有没有帮助文本，还要检查能否看全，以及查询本身是否保持只读。配置坏了时尤其如此——如果必须先成功加载配置才能查看修复用法，帮助就在最需要它的时候消失了。

同一份动作目录，提供不同深度的入口

当前 command-catalog 提供简短的 name/desc，供建议栏与 Help 等入口共享；详细参数放在 command-help，不再另建一套分派逻辑。Composer 用补全降低记忆要求，Help 让用户浏览全貌，具体用法再展示参数与前置条件。

图 11：同一个动作可以逐步被发现；查询用法不应越过业务执行边界。自然语言仍负责开放研究，不要求每个分析都映射为 slash 命令。

Help 改为全宽 Commands / Hotkeys 两类视图，Tab 或 Shift+Tab 切换，各自保留选择位置。Commands 中 Enter 执行动作，? 查询用法；Hotkeys 只是快捷键参考，Enter 与 ? 不应突然执行其中描述的操作。界面必须把这种区别写在可见提示中，否则分类反而会制造新的按键歧义。

具体帮助在配置读取与业务动作之前返回。/help COMMAND 与 /COMMAND --help 共享用法；无效参数也尽可能在切换活动、初始化模型或刷新行情前被拒绝。于是用户可以在损坏配置下查询用法，不必先修好系统才能学会如何修它。

这套设计没有把所有文档塞进补全列表。简短建议帮助定位动作，详细帮助解释怎样操作，诊断 schema 再描述选定端点的输入。层级更多，维护也更严格：目录、说明、键位提示和实际分派必须保持一致。

入口数量受到控制，学习成本仍然存在

历史回归覆盖 60×20、80×24、120×32 的全文可达、选择和视图切换，并验证从 /hel 补全到查询 /exit 用法不会退出、不会初始化模型或刷新行情。真实 CLI 子进程还在故意损坏的设置下验证帮助返回与文件不变。这些机制可由预检回归继续检查，本轮未重跑产品测试。

这些证据证明“能够发现且不误执行”的具体机制，不证明用户一定理解 Commands 与 Hotkeys，也不证明十条就是最优数量。精确命令直接提交、部分输入先补全的规则，同样需要用户建立预期。

当前取舍把确定性控制留给明确命令，把开放分析留给自然语言。它避免顶层入口随工具数量一起增长，却把一部分参数表达责任留给研究对话。如果用户反复不知道怎样写比较任务，应先观察他们缺的是示例、参数提示还是稳定表单，再决定是否增加入口；不能仅因工具已经存在，就为它自动生成一个按钮或命令。

功能发现的目标不是展示产品会多少件事，而是让用户在当前问题下，找到一个可预测的下一步。

错误出现以后，用户还能做什么？

初稿 2026-10-13 · 修订 2026-10-13 · oh-my-quant · Markdown 原文

一条错误被正确捕获，只说明程序没有继续走错。对正在工作的用户，还需要回答另一组问题：哪里失败了，刚才的输入还在吗，现在可以重试、修改，还是安全退出？

错误应该解释损失，而不只是宣布失败

数据配置同时涉及市场、来源、凭证、端点与样本。一个统一的“连接失败”很容易实现，却不能说明应当检查哪一层。反过来，把完整底层异常塞进界面，也可能让用户淹没在与下一步无关的细节里。

第 02 篇讨论保存、诊断和研究的成功语义。这一篇关心这些语义如何变成用户可以处理的状态。错误反馈至少需要说明作用范围，以及哪些工作没有丢失；下一步动作则必须与已知原因匹配，不能把所有问题都推成“换一个 key”。

这不要求应用假装知道根因。尚未分辨时，明确说哪项检查失败、哪项未测，比一个过度确定的修复建议更可靠。

诊断已经完成，修复建议却到不了用户眼前

2026-09-15 的 Doctor 视图会按面板高度停止绘制。前面的模型 warning 足够多，后面的数据失败、修复建议与操作就全部被截掉；方向键也无法滚动。后台已经生成了报告，用户却没有办法读到与故障相关的部分。这条失败路径成为Doctor 导航回归的检查对象。

另一次生产 PTY 检查暴露的是摘要问题：只检查数据阶段并通过，不能展示成整个系统通过。后来标题明确显示 data pass · model+tools untested，让未测试状态不会被一个成功标记吞掉。

这两类问题分别发生在空间和语义上。仅修滚动，仍可能让用户误信总状态；仅修标题，仍可能读不到下一步建议。反馈要可见，也要准确描述它覆盖的范围。

让细节滚动，让操作和当前工作留下

当前 Doctor 将长正文交给独立视口，阶段摘要和操作区固定，方向键、翻页、Home/End 支持逐层阅读。面板控制器继续负责检查、配置和取消；浏览报告不会重新发起网络请求。于是“我想看清楚发生了什么”不会意外变成“再执行一次”。

图 12：诊断视口与数据草稿的职责示意。保留草稿不等于自动保存；取消结束当前检查，不撤销此前已经显式提交的设置。

数据编辑使用另一条明确边界：用户改的是草稿，Check 验证当前样本，Save verified 保存与成功检查匹配的版本。修改来源、参数或凭证会使旧证据失效；取消或关闭使迟到结果不能重新授予保存资格。一次端点成功也不会被提升成所有工具、所有市场都可用。数据草稿

输入错误则尽量留在操作发生的位置。Settings 的编辑区域保留草稿与字段，错误另有空间，Enter save / Esc cancel 保持可见。用户可以修正刚才的内容，而不是因为一次校验失败重新输入整段配置。

OAuth 退出曾暴露一个更隐蔽的完成边界：凭证文件已经删除，文件锁却还在异步释放。原 UI 测试等待文件消失和一次 tick 就继续按键，偶发地找不到 Use API key。问题不是再等几毫秒，而是等待对象选错了；测试后来等待已有 Sign out Promise，并用可控门槛检查“文件已删、操作未完”时仍不能切换。这次修正没有修改生产退出逻辑，也没有加大超时。退出回归

另一次 Windows 崩溃接管失败确实属于实现：多个请求争抢过期凭证锁时，mkdir 与 rmdir 都可能短暂被拒绝。修正只对该凭证锁路径的这两类竞争做有界重试，保留取消和总等待上限；不是把全部文件错误吞掉重试。远端已轮换而响应丢失，仍可能只能重新登录。恢复机制应明确能恢复到哪里，而不是用一次重试成功许诺所有账号都不会丢失。凭证锁

这里的保留有边界：返回父面板不会撤销先前已提交的保存，关闭尚未保存的草稿也不是一次提交。界面要区分“退出编辑”“取消检查”和“撤销设置”，不能把三个含义都放在一个模糊的 cancel 上。当前契约没有提供通用设置撤销历史，也不应让用户误以为存在。

恢复路径更明确，也多了一套状态要维护

长报告修复曾引入一个真实回归：新增 Home/End 绑定抢占了 JSON 编辑器的按键，后来改为复用既有编辑键位。一个面板更好滚动，不应让另一个面板更难编辑。这是恢复体验的维护成本，而不是最后补几条友好文案就能结束的工作。相关键位行为仍须由导航与编辑回归共同约束。

现有回归分别检查报告内容可达、重试/关闭的视口重置、无效输入保留，以及取消后结果隔离。它们支撑的是这些有限行为，没有测量真实用户定位故障需要多久，也没有保证每条供应商错误都有准确的自动修复建议。

值得继续跟踪的是：用户是否能指出失败阶段，是否知道哪些设置已经保存，修正一次输入后能否直接继续，以及重试是否产生重复副作用。若这些问题答不清，堆更多异常详情也不会自动改善体验。

错误不是正常路径之外的附属页面。在依赖模型和外部数据的产品里，失败、等待、取消与恢复本来就是工作流的一部分。设计的任务，是让用户仍然知道自己在哪里、保住了什么，以及下一步能做什么。
